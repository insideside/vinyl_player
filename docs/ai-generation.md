# Локальная AI-генерация музыки — проработка

Статус: **план, код не написан.** Составлено 2026-09-09.
Ничего в `vinyl_player.py` пока не менялось, ACE-Step не установлен.

## Задача

Прикрутить к плееру локальную генеративную модель — так, как это устроено в Suno:
дать текстовый промпт, при желании подложить референс (кусок существующего трека)
и получить свою композицию. Конкретные требования:

* отдельный AI-сервер, **запускаемый из самого плеера**, а не руками;
* интерфейс генерации внутри приложения;
* результаты складываются в **отдельное хранилище вне основной библиотеки**,
  с возможностью перенести понравившееся в библиотеку;
* в контекстном меню трека библиотеки — «отправить в AI» и сразу начать генерацию;
* генерация по промпту, с референсом и без.

## Выбор модели

**ACE-Step 1.5** (январь 2026, MIT). Единственный кандидат, у которого сходится
всё сразу: открытая лицензия, официальная поддержка Apple Silicon, REST-API из
коробки и — главное — режимы работы **от существующего аудио**, а не только
text-to-music.

Режимы (одни и те же веса, Omni-Task):

| Режим | Что делает | Наш сценарий |
|---|---|---|
| text-to-music | промпт → трек | генерация без референса |
| cover / audio2audio | референс + сила влияния | «сделай своё по мотивам этого» |
| extend | продолжить аудио за его границы | достроить трек |
| repaint | перегенерировать окно по времени | правка куска |
| track extraction / layering | разделение и наслоение дорожек | пока не нужно |

Плюс попутно вытаскивает BPM, тональность и размер — пригодится для тегов
сгенерированного файла.

Варианты весов: DiT **2B** (`base` / `sft` / `turbo`) и **XL 4B**, отдельно
планирующая LM на Qwen3 (**0.6B / 1.7B / 4B**). На Mac LM идёт через MLX,
диффузия — через PyTorch MPS.

### Почему не остальные

| Модель | Лицензия | Почему мимо |
|---|---|---|
| LeVo 2 | Tencent, non-commercial | звучит лучше всех открытых, но нет remix/cover-режимов и лицензия неудобная (для личного плеера — не блокер, но и выгоды нет) |
| Magenta RealTime 2 | Apache-2.0 | 230M идёт в реальном времени на любом Apple Silicon, но это инструмент для живого джема, а не «переработай этот трек» |
| DiffRhythm 2 | Apache-2.0 | быстрая полноразмерная генерация, аудио-обусловленности почти нет |
| YuE 7B | Apache-2.0 | ~12× медленнее реального времени, тяжелее ACE-Step без выигрыша |
| MusicGen | MIT | есть честный continuation от затравки — буквально исходный запрос, — но качество 2023 года; запасной вариант |
| Stable Audio Open | своя | короткие фрагменты, слабее по музыке |

Известный дефект ACE-Step, о котором стоит знать заранее: «металлический»
призвук на вокале. На инструментале не мешает.

## Требования к железу

Машина: **MacBook Pro, M4 Pro, 48 ГБ, 1.4 ТБ свободно** — заметно выше
рекомендованного конфига (просят «M2 Pro+ и 32 ГБ»).

Чужие замеры (своих нет):

| Задача | M1 Pro 16 ГБ | M3 Pro 36 ГБ | A100 |
|---|---|---|---|
| 30 с, turbo (8 шагов) | ~45 с | ~25 с | ~2 с |
| 30 с, SFT (50 шагов) | ~3 мин | ~1.5 мин | ~8 с |
| LM 0.6B, рассуждение | ~10 с | ~5 с | ~1 с |

Apple Silicon в целом в 10–20 раз медленнее A100. Ожидание для M4 Pro: **десятки
секунд на 30-секундный отрывок в turbo, единицы минут на полный трек в качестве.**
Это надо заложить в интерфейс: генерация — заведомо долгая операция с прогрессом,
а не запрос-ответ.

Память: 48 ГБ позволяют не жаться — LM 1.7B и, вероятно, XL 4B без offload
(для XL обычно просят 20–24 ГБ). На 16 ГБ упираются в `MPS backend out of memory`;
лечится `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0`, нам скорее не понадобится.

Диск: ~15 ГБ веса, ~25 ГБ с запасом.

### Окружение на момент проработки

Ничего не готово:

* `uv` — нет;
* Python **3.11** — нет (в системе 3.13.14, а ACE-Step требует именно 3.11.x);
* репозиторий не склонирован, весов нет.

То есть установка — отдельный этап на ~час, и делать её надо явно, а не молча
в фоне первой генерации.

## Ресурсы: сколько это стоит

Размеры весов — фактические, из HuggingFace API (сентябрь 2026), а не из README.
Всё, помеченное «оценка», не проверено на месте.

### Диск: веса

| Компонент | Размер | Нужен? |
|---|---|---|
| **`Ace-Step1.5` — базовый комплект** | **10.09 ГБ** | да, это минимум |
| ├ DiT 2B turbo | 4.8 ГБ | |
| ├ LM 1.7B (планировщик) | 3.7 ГБ | |
| ├ Qwen3-Embedding-0.6B | 1.2 ГБ | |
| └ VAE | 0.3 ГБ | |
| `acestep-v15-sft` — 2B в качестве | +4.79 ГБ | желательно |
| `acestep-5Hz-lm-0.6B` — лёгкая LM | +1.37 ГБ | нет, если хватает 1.7B |
| `acestep-5Hz-lm-4B` — тяжёлая LM | +8.43 ГБ | нет |
| `acestep-v15-xl-turbo` / `xl-sft` | +19.95 ГБ каждая | нет |
| `acestep-captioner` / `transcriber` | +22.38 ГБ каждая | нет (авто-теги и распознавание лирики) |

Дополнительно к весам:

| Что | Размер |
|---|---|
| Python 3.11 + `uv` | ~0.15 ГБ |
| venv: torch (MPS), MLX, transformers, librosa, gradio/fastapi | **2–4 ГБ (оценка)** |
| MLX-конверсия LM 1.7B (отдельная копия, 4/8 бит) | 1–2 ГБ |

**Итого разумный минимум: ~14–17 ГБ. С SFT для качества: ~19–22 ГБ.**
Полный комплект с XL — под 45 ГБ, и он не нужен: XL требует ≥24 ГБ видеопамяти
по тирам разработчиков, на Mac это половина машины ради прироста, который на
инструментале почти не слышен.

### Диск: результаты

WAV 48 кГц стерео — **11.5 МБ/мин**, то есть трёхминутный трек ≈ **35 МБ**,
сотня треков ≈ **3.5 ГБ**. Хранить сырой WAV не надо: складывать сразу во FLAC
(примерно вдвое меньше) или в mp3 320 (7 МБ на трек). Это решение уровня
интеграции, не модели.

### ОЗУ

Единственный живой замер — чужой, с M2 Air 16 ГБ на конфигурации по умолчанию
(turbo 2B + LM 1.7B): `MPS allocated: 11.74 GiB, other allocations: 9.95 GiB`.
То есть процесс запросил **~21.7 ГБ** и упал по лимиту 18.13 ГБ.

| Состояние | Оперативка |
|---|---|
| сервер поднят, модель не загружена | ~0.5–1 ГБ |
| модель загружена, простой | **~10–12 ГБ держатся постоянно** |
| генерация, базовый комплект | **пик ~20–22 ГБ** |
| генерация, XL 4B | ~30–36 ГБ (оценка) |

На 48 ГБ базовый комплект проходит с запасом: в пике занято меньше половины,
25+ ГБ остаётся браузеру, плееру и системе. XL — только разовые опыты с
закрытым всем остальным.

Пик растёт с длиной трека: латент диффузии линеен по времени, и 10-минутная
генерация тяжелее 30-секундной примерно во столько же раз. Ограничение
длительности в интерфейсе — это не косметика, а защита от OOM.

Отсюда же требование выгружать модель по простою: 10–12 ГБ, занятые круглосуточно
ради кнопки, которую жмут раз в день, — плохая сделка.

### Процессор и время

Считает **GPU через MPS** (диффузия) и MLX (планирующая LM); CPU занят подачей
данных и частью декодирования VAE — то есть загружены пара ядер, а не все.
Настоящее узкое место — пропускная способность единой памяти (у M4 Pro 273 ГБ/с).

Время на генерацию, экстраполяция с опубликованных замеров M3 Pro (36 ГБ);
своих цифр нет, проверять через `profile_inference.py --device mps --lm-backend mlx`:

| Что генерируем | turbo (8 шагов) | SFT (50 шагов) |
|---|---|---|
| 30 секунд | ~20 с | ~1–1.5 мин |
| 3 минуты | ~2–2.5 мин | ~7–9 мин |

Вывод для интерфейса: **turbo — рабочий режим, SFT — «поставил и ушёл».**

Пока идёт генерация, GPU занят полностью: ноутбук греется, вентиляторы слышно,
автономная работа сокращается заметно (по опыту такой нагрузки — часы, а не
десятки часов). Это самая тяжёлая вещь, которую приложение когда-либо делало,
и это надо честно показывать в интерфейсе, а не прятать за спиннером.

### Что это значит для самого плеера

Сервер плеера однопоточный и почти не ест CPU — конкуренции за процессор нет.
Но за память и её полосу — есть, и во время генерации сканирование каталога,
стриминг и прогрев обложек станут заметно медленнее. Механизм для этого уже
есть: `relWarmArt` умеет вставать при играющей музыке, туда же вешается и
«идёт генерация».

## Архитектура интеграции

### Отдельный процесс — не обсуждается

`vinyl_player.py` — **однопоточный** `BaseHTTPRequestHandler` (см. CLAUDE.md,
«Два сервера, два порта»). Генерация на 1–3 минуты внутри него наглухо
заблокирует стриминг, обложки и вообще все запросы. Поэтому:

* ACE-Step живёт в своём процессе (`uv run acestep-api`, REST на **8001**),
  плеер его только запускает, опрашивает и глушит;
* плеер к нему ходит `POST` и **сразу** возвращает клиенту id задания;
* прогресс — по уже обкатанному в проекте образцу «фоновый поток + опрос с
  клиента», как сделано для обновления релизов в DROPS;
* модель поднимать лениво и выгружать по простою: держать 4B резидентно ради
  кнопки, которую жмут раз в день, смысла нет.

### Где лежат результаты

Предложение: **`~/.vinyl_ai/tracks/`** — обычная папка с аудиофайлами плюс
`~/.vinyl_ai/jobs.json` (журнал заданий: промпт, референс, параметры, время,
имя файла).

Ключевая мысль: приложение **уже умеет несколько каталогов**
(`get_user_folders`, `last_folder`, `_user_music_dirs`, `/api/scan?path=`).
Если AI-хранилище — это ещё один каталог, то плеер, очередь, кэш в IndexedDB,
поиск, окно метаданных и контекстное меню работают там **сразу и бесплатно**,
без единой новой строчки. Альтернатива — свой список со своей очередью — требует
дублировать `tracks[]` / `playQueue` / `cachedFiles`, а это много кода и много
мест, где сломается.

Перенос в библиотеку тогда — пункт контекстного меню с подменю каталогов:
переместить файл + перенумеровать, ровно как это уже делает импорт
(`vk_renumber_tracks`, `repair_playlist_refs`).

### Что добавляется на сервере

Новый блок перед классом `Handler`, по образцу блока «Новинки артистов»:

| Ручка | Назначение |
|---|---|
| `GET /api/ai/status` | установлено ли, поднят ли сервер, модель, очередь, задания |
| `POST /api/ai/install` | поставить uv / Python 3.11 / репозиторий / веса, с прогрессом |
| `POST /api/ai/server` | `{action: start\|stop}` |
| `POST /api/ai/generate` | промпт, лирика, длительность, режим, референс, сила |
| `GET /api/ai/jobs` | состояние заданий |
| `POST /api/ai/cancel` | снять задание |
| `GET /api/ai/tracks` | список сгенерированного |
| `GET /api/ai/stream/<file>` | отдача файла (свой путь: библиотечный `/api/stream/` заперт в каталоге пользователя) |
| `POST /api/ai/track/delete` | удалить |
| `POST /api/ai/track/import` | перенести в выбранный каталог библиотеки |
| `POST /api/ai/settings` | путь установки, вариант модели, порт |

Настройки — в общий `~/.vinyl_settings.json` (он уже 600 и уже про сервер).

### Что добавляется на клиенте

* **Окно генерации** — по образцу окна импорта (`openVkModal` / `showImpTab`):
  промпт, необязательная лирика, длительность, вариант модели (turbo/качество),
  референс (файл из библиотеки или ничего) и ползунок силы влияния.
* **Пункт контекстного меню трека** — «Сгенерировать по этому треку»: открывает
  то же окно с уже подставленным референсом. Живёт рядом с «Играть следующим»
  и виден только когда AI-сервер поднят.
* **Раздел AI** — где именно, см. открытый вопрос ниже.
* **Раздел в профиле** — состояние окружения, кнопка установки, старт/стоп
  сервера, выбор модели. По образцу спойлера «Графика» (`perfCfg` / `perfApply`).

## Открытые вопросы

1. **Ставить ACE-Step сразу или сделать кнопку установки в интерфейсе.**
   Кнопка честнее: ~15–25 ГБ и до часа не должны качаться без ведома. Но пока
   модели нет, интеграцию не проверить вживую.
2. **Как показывать AI-треки: особым пунктом в переключателе каталогов или
   пятой вкладкой рядом с DROPS.** Первое почти бесплатно и переиспользует всё,
   второе заметнее, но требует дублировать плеер, очередь и кэш.

## Ловушки, известные заранее

* **Сервер однопоточный** — всё тяжёлое только в отдельном процессе. Это же
  касается установки: `uv sync` и скачивание весов нельзя делать в обработчике
  запроса.
* **Python 3.11–3.12.** В системе 3.13 — ACE-Step на нём не встанет,
  интерпретатор придётся ставить отдельно (`uv python install 3.11`).
  Сторонний порт на Apple Silicon требует строго 3.11.x, официальный — 3.11–3.12.
* **`/api/stream/` не годится для AI-треков**: он проверяет, что каталог входит
  в `get_user_folders`, и заперт в текущей папке пользователя. Нужна своя ручка
  со своим `_safe_path` внутри `~/.vinyl_ai/tracks`.
* **`/api/scan` пускает вне `music_root` только админа.** Если AI-каталог
  делать обычным каталогом, для не-админа понадобится явное послабление именно
  для этого пути.
* **Сгенерированный файл без тегов** выглядит в списке как «Unknown». Теги
  (title из промпта, artist, год, BPM/тональность из ответа модели) надо
  проставлять сразу через существующий `write_metadata_to_file`.
* **Офлайн.** Генерация — операция с записью на сервер, значит офлайн она честно
  отказывает, как правка тегов и перемещение файлов. Откладывать её в очередь
  бессмысленно: она требует живого локального процесса.
* **Процесс-сирота.** AI-сервер, поднятый плеером, обязан гаситься в
  `_shutdown_cleanup()` — иначе после выхода останется висеть процесс,
  державший гигабайты весов.
* **Виджет и энергопотребление.** Генерация греет машину сильнее всего, что
  приложение делало до сих пор. Стоит сразу предусмотреть, что при работающей
  генерации прогрев обложек DROPS (`relWarmArt`) встаёт — он и так стоит при
  играющей музыке, механизм есть.

## Порядок работ, когда возьмёмся

1. Раздел AI в профиле: определение окружения, установка по кнопке с прогрессом.
2. Управление процессом ACE-Step: старт, стоп, health-check, гашение при выходе.
3. Очередь заданий и ручки генерации; складывание результата в `~/.vinyl_ai/tracks`
   с проставлением тегов.
4. AI-каталог в интерфейсе + перенос в библиотеку.
5. Окно генерации и пункт контекстного меню с референсом.
6. Замер на месте: `python profile_inference.py --device mps --lm-backend mlx`,
   цифры — в этот файл.
