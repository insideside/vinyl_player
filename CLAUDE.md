# insideside music — заметки по кодовой базе

Контекст для работы над кодом. Пользовательская документация — в `README.md`, здесь её не дублируем.

## Что это

Локальный музыкальный веб-плеер: Python-сервер на `http.server` + одностраничное приложение,
которое ставится на iPhone как PWA. Импорт треков из VK/Яндекс/Spotify/Apple Music/SoundCloud,
поиск метаданных, плейлисты, офлайн-кэш, раздача по LAN/WAN.

## Архитектура: один файл

`vinyl_player.py` — ~14 200 строк, **всё приложение целиком**: сервер, HTML, CSS и JS.
Фронтенд живёт в Python-строках верхнего уровня:

| Блок | Что это |
|---|---|
| `SW_JS = r"""..."""` | Service Worker |
| `HTML_PAGE = r"""..."""` | всё приложение: разметка, стили, ~5000 строк JS |
| `LOGIN_PAGE = r"""..."""` | страница входа |

Плейсхолдеры подставляются при отдаче: `PORT_PLACEHOLDER` и `APP_BUILD_HASH` в `HTML_PAGE`,
`BUILD_HASH` и `SW_PORT` в `SW_JS`. `APP_BUILD_HASH` — это `md5(HTML_PAGE)[:8]`, он же ключ
SW-кэша и основа автообновления через `/api/version`.

Прочее: `android/` (обёртка Chaquopy), `macos-widget/` (виджет Übersicht),
`vk_music_downloader.py` (отдельная утилита), `build_*.sh|bat` (сборка).

## Два сервера, два порта

| Порт | Адрес | Схема | Кто ходит |
|---|---|---|---|
| `LOCAL_PORT = 7666` | `127.0.0.1` | всегда **HTTP** | Mac-приложение, виджет, локальный браузер |
| `SERVER_PORT = 7656` | `0.0.0.0` | **HTTPS** когда LAN включён | телефоны, другие устройства сети |

Локальный сервер работает всегда; LAN-сервер поднимается только при `IS_PUBLIC`. Разделение
намеренное: локальную точку входа нельзя ломать переключением LAN. Локальный URL открывается
по имени `localhost`, а не `127.0.0.1` — иначе браузер, увидев HTTPS на `127.0.0.1:7656`,
пинит HSTS на весь хост и апгрейдит даже HTTP-порт.

Оба используют `BaseHTTPRequestHandler` и **однопоточны**. Один долгий стрим блокирует все
остальные запросы — это заметно при массовом кэшировании и при отладке.

## HTTPS и сертификат

Самоподписанный, `~/.vinyl_cert.pem` / `~/.vinyl_key.pem`. SAN содержит все локальные IP,
`localhost` и mDNS-имя машины. Перевыпуск — только когда сертификата нет, он истекает или
не покрывает текущие адреса.

**Ловушка:** системный `openssl` в macOS — это LibreSSL, в нём **нет флагов `-ext` и `-addext`**.
Поэтому генерация идёт через `cryptography`, а чтение SAN — через `-text` (или ту же
`cryptography`). Раньше проверка покрытия падала в `except` и сертификат перевыпускался при
каждом запуске, из-за чего на iPhone приходилось заново принимать доверие.

**Ловушка:** TLS-ошибки рукопожатия (`_ssl_error_count`) **не повод** перевыпускать сертификат.
Это почти всегда клиент, который его ещё не принял; перевыпуск делал только хуже — получалась
петля, а текущие загрузки рвались.

## Адреса подключения и PWA

PWA намертво привязана к origin, с которого установлена. Установили по `https://192.168.1.101:7656` —
в другой Wi-Fi сети IP другой, приложение стучится в мёртвый адрес, а кэш (IndexedDB + Cache
Storage) привязан к origin и переехать не может.

Поэтому сервер отдаёт `lan_host_url` — стабильный адрес по mDNS-имени (`<имя>.local:7656`).
Имя определяется в рантайме (`scutil --get LocalHostName` в macOS, иначе `socket.gethostname()`)
и **отдаётся только если сервер сам может его разрезолвить**: `.local` работает лишь при живом
mDNS-ответчике (в macOS есть всегда, в Linux нужен avahi, в Windows — Bonjour). В сертификат
имя кладётся всегда. Результат кэшируется на 5 минут — `get_lan_host_url()` дёргается на каждом
`/api/config`, а внутри subprocess и DNS-запрос.

Safari и iOS резолвят `.local` через системный mDNS, **Chrome — нет** (свой DNS-резолвер,
даёт `DNS_PROBE_FINISHED_NXDOMAIN`). В подсказках это оговорено.

Спасательные пути, когда origin умер: диалог «Подключение к серверу» (профиль → «Адрес сервера»
или тап по офлайн-баннеру) и поле ввода адреса на SW-странице «Сервер недоступен».

## Хранилище на клиенте

**localStorage** (всё привязано к origin):

| Ключ | Что |
|---|---|
| `_vc_config` | последний конфиг с сервера |
| `_vc_folder_<путь>` | закэшированный каталог треков (~1 МБ на 2500 треков в UTF-16) |
| `_vc_playlists_<путь>` | плейлисты каталога |
| `_vc_hosts` | адреса серверов, введённые вручную |
| `_vc_playctx` | текущий трек и позиция (переживает перезапуск PWA) |
| `_vc_cachequeue` | остаток очереди кэширования |
| `_vc_player_mode` | вид плеера |
| `_vc_reltab` | выбранная подвкладка DROPS |
| `_vc_rellimit` / `_vc_fylimit` | размер порции NEW и 4YOU |
| `_vc_eras_<путь>` | зеркало разметки периодов |

Квота origin — ~5 МБ, каталоги её съедают. Все записи идут через `lsSet()`, который при
переполнении вытесняет самые крупные `_vc_folder_*` и повторяет попытку: каталог всегда можно
пересканировать, плейлисты и конфиг — нет.

**IndexedDB** `vinylCache`, стор `audio` — плоский, `ArrayBuffer` по строковым ключам:
* аудио — ключ `cacheKey(file)`
* обложка — ключ `'cover:' + cacheKey(file)`

`cacheKey()` срезает префикс `NN. `: файлы на диске нумерованные, добавление трека
перенумеровывает весь каталог, и полное имя как ключ нестабильно. Блобы при этом **не
переносятся** — копирование ~1 ГБ роняет PWA на iOS; вместо этого `refreshCachedList()` строит
индексы `_audioKeyIndex` / `_coverKeyIndex` по одному только списку ключей.

**IndexedDB** `vinylNew`, стор `kv` — зеркало раздела DROPS, отдельная база, чтобы не трогать
версию `vinylCache` (её открывает ещё и Service Worker, и рассинхрон версий уронил бы его):

| Ключ | Что |
|---|---|
| `feed` | последняя синхронизированная лента NEW + `saved_at` |
| `feed4you` | то же для ленты 4YOU |
| `artSeen` | адреса уже загружавшихся обложек релизов |
| `starred` | избранное, снимки релизов |
| `pendingStars` | отметки, поставленные без сервера, ждут отправки |
| `pendingPlays` | прослушивания без сервера, ждут отправки |
| `plays:<путь>` | зеркало счётчиков каталога (для умных плейлистов офлайн) |

| Путь | Что | Права |
|---|---|---|
| `~/.vinyl_users.json` | учётные записи | 600 |
| `~/.vinyl_settings.json` | LAN/WAN, корень музыки | 600 |
| `~/.vinyl_cert.pem` / `~/.vinyl_key.pem` | самоподписанный HTTPS | 600 |
| `~/.vinyl_releases.json` | кэш новинок, общий для всех | 600 |
| `~/.vinyl_starred.json` | избранное **по пользователям** | 600 |
| `~/.vinyl_plays.json` | история прослушиваний по пользователям и каталогам | 600 |
| `~/.vinyl_release_art/` | обложки релизов, вытеснение по mtime | 700 |
| `<каталог музыки>/.vinyl_playlists.json` | плейлисты каталога | — |
| `<каталог музыки>/.vinyl_eras.json` | разметка периодов прослушивания | — |

Всё, что меняет данные (плейлисты, удаление, перемещение, теги), — это запись на сервер;
очереди отложенных записей нет, офлайн такие действия честно отказывают. Исключение —
избранное в DROPS: оно копится локально и досылается.

## Ловушки, на которые уже наступали

**Ответ 200 ≠ полезные данные.** При истёкшей сессии `/api/*` отдаёт `{"error": "unauthorized"}`
со статусом **200**. Проверка `if (!r.ok)` это не ловит: 25 байт JSON попадали в IndexedDB как
обложка или как трек — навсегда, потому что «закэшировано» и повторно никто не качал. Сейчас
`/api/cover/` и `/api/stream/` отдают честный **401**, клиент проверяет `Content-Type` и
сигнатуру файла при записи и при чтении, испорченные записи чинятся сами.

**Service Worker маскирует падение сервера.** На неудачный `/api/*` он возвращает **200 с
`{error:'offline'}`**. Поэтому `r.ok` и отсутствие reject ничего не значат: нужно смотреть на
тело. Из-за этого `userPlaylists = d.playlists || []` затирал кэш плейлистов пустотой, а
страница «Сервер недоступен» уходила в цикл перезагрузок по `r.ok`.
SW **не перехватывает** `/api/stream/`, `/api/cover/`, `/reset`, `/icon.png` и любой
кросс-доменный запрос (иначе проба чужого адреса всегда выглядит успешной).

**Обновление доходит до клиента только со второго раза** — так было до фикса.
Обработчик главной страницы в SW отдаёт кэш сразу (`return cached`), а свежую
версию кладёт в кэш фоном, поэтому первое обновление показывало старую сборку.
Теперь при активации нового воркера (то есть нового билда) он рассылает открытым
вкладкам `postMessage({action:'reload'})` — клиент это сообщение слушал всегда,
но никто его не слал. Рассылка только при обновлении, не при первой установке.
Проверка: поднять сервер, закэшировать страницу, изменить `HTML_PAGE`,
перезапустить сервер, обновить страницу **один** раз — правка должна быть видна.

**`OFFLINE_FALLBACK` внутри `SW_JS` — строка в одинарных кавычках.** Каждый обратный слэш
съедается JS-строкой раньше, чем браузер разберёт HTML: регулярка `/\/+$/` приезжает как
`//+$/` и комментирует остаток скрипта. **Этот блок пишем без обратных слэшей вообще.**
Проверка: `eval` строкового литерала, затем `node --check` вытащенного инлайн-скрипта.

**Смена `audio.src` порождает событие `pause`.** Отличить её от системного прерывания можно
только флагом — все присвоения идут через `setAudioSrc()`, флаг снимается по `loadstart`.
Эвристика по `readyState` не работает: приложение подменяет src на blob уже после старта.

**`scrollTo({behavior:'smooth'})` в Chrome на длинных списках с ленивыми картинками молча
не срабатывает** (побеждает scroll anchoring). В Safari работает. Поэтому — фолбэк на
мгновенную прокрутку, если через 250 мс позиция не сдвинулась.

**Обрыв связи не должен прокручивать очередь вхолостую.** `fetch` падает мгновенно, и цикл
кэширования за секунды «проходил» сотни треков, ничего не скачав. `cacheTrack` различает
причины: `http` (сервер ответил «нет» — трек пропускаем), `net` (связь/TLS — файл остаётся
в голове очереди, повторы с паузой, затем остановка), `db` (хранилище переполнено).

**Офлайн-записи есть, но не для всего, и правило несимметричное.**
Создание, переименование, добавление треков и порядок плейлистов копятся в
`pendingPlaylists` и досылаются при подключении (`flushPlaylists`, рядом с
`flushPlays` и `flushEras`). **Удаление не откладывается никогда:** сервер здесь
истина, а на клиенте легко нажать не то — разослать случайную потерю по всем
устройствам хуже, чем не выполнить удаление. Удалённое без сети возвращается при
первой же синхронизации, потому что список просто перечитывается с сервера.

Плейлисту, созданному без сети, выдаётся временный id (`plTempId`): показать и
дать править его нужно сразу, а свой id сервер присвоит при досылке, после чего
список перечитывается. Правка такого плейлиста **вливается в его же `create`** в
очереди — отдельный `update` сервер не понял бы, у него нет такого id.

Все записи идут через `plWrite`; прямые `fetch` к `/api/playlists` остались
только у чтений списка, у самих отправителей очереди и у двух удалений.

Правка тегов и перемещение файлов по-прежнему офлайн не работают.
Раньше отказ показывался как голое «offline»: SW подменяет неудачный `/api/*`
телом `{error:'offline'}`, и код утекал в тост из полутора десятков мест. Теперь
перевод делается один раз в `showToast`. Окно редактирования плейлиста при
отказе **не закрывается** — иначе собранный список треков пропадал.

**Индикатор офлайна при живом Wi-Fi.** `navigator.onLine` остаётся `true`, когда недоступен
только сервер, — событие `offline` не придёт. Ловим по телу ответа `/api/config` и `/api/version`.

**Поиск.** Отображаются теги (`title`/`artist`), а имя файла на диске пишется иначе
(`Smack That (Slowed & Reverb).mp3` против тега `Smack That(Slowed & Reverb)`, `Артист, Артист`
против `Артист/Артист`). Поэтому в стог сена входят оба источника, пунктуация схлопывается
в пробелы, слова матчатся по «И».

## DROPS: две ленты, NEW и 4YOU

Внутри вкладки две подвкладки (переключатели в строке с количеством дропов):

* **NEW** — новинки артистов библиотеки, всё свежее `RELEASES_WINDOW_DAYS`;
* **4YOU** — остальной каталог тех же артистов: то, что старее окна и чего в
  библиотеке ещё нет.

**4YOU не заводит ни своего кэша, ни своих запросов к API.** iTunes отдаёт по
25 последних релизов на артиста, а новинками из них считаются только последние
400 дней — всё остальное уже лежало в `~/.vinyl_releases.json` и просто нигде
не показывалось. На этой библиотеке: 1821 запись в NEW, 5297 в 4YOU, ноль
дополнительных обращений к сети. Обе ленты идут через одну ручку
`/api/releases?mode=new|foryou`; общее — `_feed_library`, `_feed_dedup`,
`_feed_add_starred`, `_feed_envelope`.

**Ранжирование 4YOU — по кругу артистов, а не сортировкой по весу.** Вес у всех
релизов одного артиста одинаковый (это `artist_score`), поэтому обычная
сортировка отдавала бы первые 25 карточек одному артисту — ровно столько его
записей лежит в кэше. Поэтому берётся лучший релиз каждого артиста, потом
второй, и так далее; внутри артиста — от свежего к старому. Клиент повторяет то
же правило в `relRoundRobin` для автономного обхода.

**Даты в 4YOU не группируют.** Там всё старее окна новинок и в группировке
`relGroupOf` попало бы в одну кучу «Раньше», поэтому `relGroupFor` отдаёт всей
ленте одну группу «Рекомендации» — заголовок печатается один раз, при смене
подписи, ровно там же, где в NEW стоит «Скоро». Избранное остаётся отдельной
группой выше.

**Отметки общие, ленты — нет.** `~/.vinyl_starred.json` один на обе, и снимок
закреплённого возвращается в ленту, только если принадлежит ей по дате
(`_feed_add_starred(..., want)`). Без этого закреплённое в 4YOU всплывало бы
наверху NEW. То же на клиенте: `relApplyStarred` берёт предикат, а
`relSaveStarredLocal` не переписывает снимок целиком — вторая лента может быть
ещё не загружена, и её отметки стёрлись бы.

**Состояние лент — в `relFeeds`, а не в одиночных переменных.** У каждой свои
`data`, `nodes`, `limit`, `mirrorKey`, `offline`, `poll`. Раздельные `nodes`
принципиальны: с общим набором переключение подвкладки пересоздавало бы все
`<img>` и обложки грузились бы заново. Асинхронные ответы адресуются ленте по
имени (`loadReleases(silent, tab)`), а рисуется только активная — иначе ответ
для фоновой ленты перерисовывал бы экран.

**После проверки артистов соседняя лента метится устаревшей, а не гасится
сразу** (`relInvalidate`). Обе растут из общего кэша артистов, но гасить ту, на
которую смотрят, нельзя: `renderReleases` с пустыми данными выходит сразу, и на
экране остались бы карточки, которых уже нет в состоянии. Активную поэтому
перезапрашиваем на месте, фоновую — просто обнуляем, зеркало остаётся.

**Ключ релиза строит `_release_key`, а не `source:rid` напрямую.** У записей из
старого кэша `rid` нет (поле появилось вместе с превью), и «itunes:None»
совпадал у всех таких сразу: дедупликация схлопывала 180 релизов в одну
карточку, а в 4YOU ключ пересекался с чужим релизом из NEW. Для безридовых ключ
строится из названия и даты. `findRelease` поэтому сравнивает `it.key`, а не
пересчитывает `relKey`.

**Кнопка «Скачать ZIP-архив» — только на вкладке «Треки»** (`syncDownloadBtn`).
Она относится к каталогу треков, а на DROPS, альбомах и плейлистах скачивать
нечего; условие живёт в одном месте, потому что кнопку дёргают из `showTab`,
применения конфига и выхода из режима выделения.

Серверная часть — блок «Новинки артистов» перед секцией плейлистов. Ключевое:
список отслеживаемых артистов **нигде не хранится**, он выводится из библиотеки
при каждом обновлении (`rank_library_artists`), поэтому переживает любое
изменение каталога. Свежесть считается **внутри каждого каталога отдельно** —
по сквозному списку второй каталог целиком получал бы низкую свежесть просто
потому, что идёт ниже.

Источники: iTunes Search API (основной), Deezer (запасной). Оба без ключей. На
этой библиотеке iTunes нашёл 17 артистов из 17, включая русский андерграунд, и
по свежести релизов обгонял Deezer на 3–12 месяцев у трети выборки.

* кэш релизов — `~/.vinyl_releases.json`, общий для всех пользователей (данные
  публичные), TTL сутки;
* «есть ли уже в библиотеке» считается **на каждый запрос**, а не кэшируется:
  библиотека меняется чаще, чем данные о релизах;
* обновление идёт в отдельном потоке с паузой ~1.2 с между запросами; сервер
  однопоточный, а полный цикл — это 60+ запросов;
* бюджет артистов за цикл — `_artist_budget()`, растёт медленнее библиотеки
  (787 артистов → 54), плюс 10 из хвоста по давности проверки;
* `/api/releases` сам поднимает фоновое обновление, если кэш протух, и сразу
  отдаёт что есть — интерфейс показывает прогресс, а не пустой экран.

Клиент: вкладка DROPS (внутренние идентификаторы остались `tabNew` / `newList` / `activeTab === 'new'` — переименован только видимый ярлык; подвкладка хранится в `_relTab`, зеркала — `feed` и `feed4you`) / панель `newList`, скрывается при `_isOffline`
(`syncNewTabVisibility`). Кнопка загрузки передаёт релиз в существующее окно
импорта: `openVkModal()` → `showImpTab('search')` → заполнить `#vkSearchQuery` →
`vkSearchTracks()`.

**Превью (30 сек).** Треки с отрывками — отдельный запрос на релиз
(`/api/releases/tracks`), поэтому дёргается только по нажатию: тянуть их для
всей ленты — это сотни лишних обращений. В записи релиза для этого хранится
`rid` (`collectionId` у iTunes, `id` альбома у Deezer); при добавлении полей в
запись поднимаем `RELEASES_SCHEMA`, иначе старый кэш останется без них.

**Срез ленты — по релевантности, не по дате.** `RELEASES_LIMIT` отдаёт лучшие
по весу `artist_score × (0.4 + exp(-возраст/120))`; будущие даты получают полный
вес. Внутри среза сортировка снова по дате — так читается привычнее.
Дедупликация обязана идти **до** среза (по ключу и по паре «название + дата»),
иначе он теряет места на дубли: совместка приходит от каждого участника, а
iTunes порой отдаёт один релиз с разными id. Клиент просит объём через
`?limit=`, кнопка «Показать ещё» увеличивает `_relLimit` на `REL_PAGE`.

**Избранное не попадает под срез.** Запись из снимка приходит без
`artist_score` (артиста уже нет в проверке), получает вес 0 и уезжала в хвост
ранжирования — отмеченная карточка исчезала из ленты. Срез применяется только к
неотмеченным.

**Раскрытие дропа — только `applyExpansion()`, не `renderReleases()`.** Полная
пересборка на миг схлопывает контейнер, браузер прижимает `scrollTop`, и с низа
списка выбрасывало в середину. Там, где пересборка законна (подгрузка, отметка),
`syncReleaseCards` запоминает и возвращает позицию.

**Обложки грузятся вручную, а не `loading="lazy"`.** Адрес лежит в `data-src`,
`relWarmArt` идёт по списку сверху вниз: **один запрос в воздухе**, пауза 250 мс,
и полная остановка, пока играет музыка. Сервер однопоточный — первый показ
каждой обложки это его поход к Apple примерно на секунду, и пачка параллельных
запросов встала бы поперёк потока воспроизведения. Проверено на однопоточном
сервере: ~1.3 обложки/с, задержка API 11–13 мс.

**Через очередь прогрева гоним только незнакомые обложки.** Прокси отдаёт их с
`max-age=30 дней`, то есть повторный показ идёт из HTTP-кэша браузера — но
очередь об этом не знала и всё равно вела каждую по 250 мс, а при играющей
музыке стояла совсем. На срезе в 300 карточек это ≥75 с проявления при каждом
открытии и выглядело как «дропы грузятся заново». Загруженные адреса копятся в
`_artSeen` (зеркалится в `vinylNew`, ключ `artSeen`, потолок `ART_SEEN_MAX`),
такие обложки получают сразу `src` вместо `data-src` и очередь их не видит.
Замер: 97 из 600 карточек с обложкой на первом кадре, ноль ожидания.

**Отказ прокси обложек — не повод рисовать заглушку.** `relArtFallback` при
первой ошибке переставляет `<img>` на прямой адрес источника (`data-direct`) и
только при второй ставит `&#9834;`. Нужно с тех пор, как лента рисуется из
зеркала **до** того, как известно, жив ли сервер: иначе при мёртвом сервере
знакомые обложки мгновенно превращались бы в заглушки, а замена идёт через
`outerHTML` и необратима. Заодно чинит случай, когда файл вытеснен из
`~/.vinyl_release_art/`.

**Не сбрасывать `_cardNodes` при загрузке ленты** — `syncReleaseCards` сам чистит
неиспользуемые ключи. Сброс убивал переиспользование узлов, и при подгрузке
следующей порции пересоздавались все обложки, а не только новые.

**Раскрытый релиз держим по ключу `source:rid`, не по индексу.** Лента
перестраивается, порядок меняется — индекс начинал указывать на чужой альбом, и
список треков «прыгал» на соседнюю карточку.

**Узлы карточек переиспользуются** (`_cardNodes`, `syncReleaseCards`): при любой
перерисовке существующие элементы переставляются во фрагмент, а не создаются
заново. Иначе каждый `<img>` рождался пустым и обложки «пропадали и появлялись»
— при клике по альбому, при отметке, при обновлении. Даже когда состояние
карточки поменялось, `<img>` переносится в новую разметку, а не пересоздаётся.

**Обложки релизов кэшируются на диск** (`~/.vinyl_release_art/`,
`/api/releases/art?u=...`). В кэше новинок лежит только URL, и без прокси
браузер ходил за картинками к Apple при каждом открытии вкладки. Хосты
проверяются по суффиксу (`.mzstatic.com`, `.dzcdn.net`) — иначе это открытый
прокси. Тип определяется по сигнатуре файла, каталог ограничен `ART_MAX_FILES`
с вытеснением по mtime.

**Автономный режим DROPS.** Проверено в браузере: **iTunes Search API отдаёт
`access-control-allow-origin: *`** и вызывается из страницы напрямую, **Deezer —
нет** (`TypeError: Failed to fetch`), обложки как `<img>` грузятся без CORS.
Поэтому лента и избранное зеркалятся в IndexedDB `vinylNew`, при мёртвом сервере
показывается копия, а «Проверить новинки» обходит артистов прямо из браузера
(`relSweepDirect`), ранжируя их по каталогам из localStorage тем же правилом,
что и сервер. Отметки копятся в `pendingStars` и досылаются `relFlushStars`,
после чего лента перезапрашивается — иначе они выглядели бы снятыми, ведь
сервер строил ответ до синхронизации. В автономном режиме `art` берётся прямым
URL, а не через `/api/releases/art`.

Ловушка, на которую наступил: в `loadReleases` стоял выход по `_isOffline` — из-за
него до зеркала дело вообще не доходило. Запрос делать безопасно: SW отвечает
`{error:'offline'}` не ходя в сеть.

**Зеркало рисуется сразу, а не только при мёртвом сервере.** `relLoadMirror`
стоял в одном `.catch()`, поэтому при живом сервере каждое открытие приложения
начиналось со спиннера «Собираю новинки…» и ждало сеть — хотя готовая копия
лежала рядом в IndexedDB. Теперь `loadReleases` сначала рисует зеркало
(`relFeedFromMirror`), а ответ сервера подменяет содержимое молча;
спиннер остаётся только когда копии ещё нет (`_relHasMirror`). Замер на
однопоточном сервере: первые карточки в DOM через **43 мс** вместо **1700 мс**.
Гонку решает проверка `if (releasesData) return` в колбэке зеркала — сеть может
успеть первой, и затирать её копией нельзя.

**`_relLimit` переживает перезапуск** (`_vc_rellimit` в localStorage, потолок
`REL_LIMIT_MAX` — столько же принимает сервер). Иначе каждое открытие PWA
откатывало ленту к первой порции и «Показать ещё» приходилось жать заново.

**Закрепления — в отдельном файле** `~/.vinyl_starred.json`, не в кэше новинок:
обновление переписывает кэш целиком в фоновом потоке и затёрло бы отметку.
Вместе с ключом хранится снимок релиза, поэтому закреплённое остаётся в ленте,
даже когда выпало из окна дат или артист вышел из проверки.

**Лента рисуется тремя блоками** (`relStatus` / `relCards` / `relFooter`), и
карточки пересобираются только при смене подписи состава. Иначе каждый тик
прогресса пересоздавал `<img>` и обложки грузились заново.

**Проверка артистов — только по кнопке.** Автозапуска нет нигде: ни по TTL, ни
по схеме, ни при пустом кэше. Была петля — `schema_stale` считался по каждому
артисту, а обновление покрывает лишь бюджет цикла, поэтому флаг не опускался и
проверка шла непрерывно. Теперь отметка схемы хранится один раз на файл и
снимается по завершении обновления. Скан библиотеки для ленты кэшируется на
120 с (`_collect_user_tracks_cached`): иначе каждое открытие вкладки читало теги
у нескольких тысяч файлов.

**Одного `RELEASES_SCHEMA` мало.** Проверка версии стоит внутри `refresh_releases`,
но само обновление запускается по TTL — а кэш может быть свежим по времени и
устаревшим по составу полей. Ровно так и вышло: записи схемы 0 лежали без `rid`,
кнопка превью не рисовалась, и починилось бы это лишь через сутки. Поэтому
`build_releases_feed` отдаёт `schema_stale`, и `/api/releases` запускает
обновление ещё и по нему.

Две ловушки, обе уже поймали:
* **`play()` после `fetch` — вне жеста.** Список треков приезжает асинхронно, и
  вызов `play()` в `.then()` браузер отклоняет с `NotAllowedError` (на iOS —
  всегда). Поэтому `togglePreview` синхронно в обработчике клика проигрывает
  `_silentBlobUrl`, разблокируя элемент, и уже потом подменяет `src`.
* **Apple отдаёт превью с `Content-Type: audio/x-m4p`,** на который
  `canPlayType` отвечает пустой строкой. Поэтому отрывки идут через
  `/api/releases/preview?u=...`, который подменяет тип на `audio/mp4`
  (`audio/mpeg` для Deezer). У прокси **закрытый список хостов** — без него это
  открытый прокси и SSRF.

Источник превью — не жёсткий: если основной ничего не отдал, `release_tracks()`
ищет тот же релиз во втором по артисту и названию (`_find_release_id`) и берёт
отрывки оттуда. На выборке из этой библиотеки Deezer нашёл 10 релизов из 10, так
что подстраховка рабочая. Все обращения к обоим API идут через `_get_json()` с
повторами: iTunes при частых запросах отвечает «Connection reset by peer», и без
повторов это выглядело бы как отсутствие данных.

Раскрытие и воспроизведение разведены: `togglePreview(key, autoplay)` без
`autoplay` только раскрывает список (клик по карточке), с ним — играет (кнопка
▶). Музыка, стартующая от простого просмотра состава альбома, перебивала
играющий плеер и мешала.

Превью играет в **отдельном** `<audio id="previewEl">`: в основном живёт контекст
воспроизведения (см. раздел про iOS), и подмена `src` ради отрывка его потеряла
бы. Основной плеер перед превью останавливается через `setPlayState(false)`
**до** `audio.pause()` — иначе обработчик посчитает это системным прерыванием.

## Дозаполнение тегов

`write_metadata_to_file` при `overwrite=False` ставит поле, только если своего в
файле нет. Пишутся title, artist, album, year, **genre, номер трека, album
artist** и обложка.

**Дефект, который тут был:** в ветке `.m4a` альбом писался без проверки
`overwrite` — единственное место, где «заполнение пустого» молча переписывало
существующий тег.

**Deezer новых полей не отдаёт.** В его ответе поиска только
id/title/artist/album/cover — ни жанра, ни номера, ни даты (проверено). А в
`search_metadata` он идёт первым и для большинства треков побеждает, поэтому
одного расширения источников мало. У iTunes же `primaryGenreName`,
`trackNumber`, `releaseDate` лежат в том же ответе, который и так запрашивается.
Отсюда `enrich_new_tags`: отдельный запрос к iTunes делается, только когда полей
не хватило, и трогает он **исключительно** новые поля.

**Жанр берём при совпадении артиста, остальное — только при совпадении
альбома.** Жанр — свойство трека и артиста, а номер трека, год и album artist
привязаны к изданию. Издания при этом считаем одним альбомом (совпадение по
префиксу): источники расходятся сплошь и рядом — «From Zero» против «From Zero
(Deluxe Edition)», — а музыка та же. Без этого послабления треть выборки
оставалась без жанра.

**Запрос строится по тегам, а не по имени файла**, если теги есть. Дозаполнение
доходит и до хорошо оттегированных файлов, а у них имя обычно хуже тега
(«088. 01 - From Zero.flac» против «Linkin Park — From Zero»).

**Условие «здесь дозаполнять нечего»** — `meta_is_complete`, и в него входят
новые поля. Раньше проверялись только исполнитель, альбом и обложка, поэтому
файл с ними пропускался навсегда и жанр в него уже никогда не попадал.

Массового прогона по библиотеке намеренно нет: новые теги читает только
`buildContinuation` (жанр +1, год +0.5 против +3 у артиста), номер трека и album
artist не читает пока никто. Дозаполнение идёт теми проходами, что уже есть, —
после импорта и по кнопке на выделенных треках.

## История прослушиваний

Файл `~/.vinyl_plays.json`, **по пользователям и каталогам**, ключ записи —
обезномеренное имя файла. Полное имя как ключ обнуляло бы историю после первого
же импорта: он перенумеровывает каталог целиком (той же болезнью болели
плейлисты, см. `repair_playlist_refs`).

**Сервер — единственный источник правды.** Клиент шлёт отметку на
`/api/plays`, не сумел — кладёт в `pendingPlays` (IndexedDB `vinylNew`) и
досылает. `flushPlays()` обходит **все** каталоги очереди, а не только
открытый: прослушивание в PWA без сети обязано доехать, даже если в этот
каталог больше не зайдут. Вызывается из `applyConfig` (то есть на старте и при
каждом переподключении) и по событию `online`.

**Отметка ставится по проигранному времени, а не по нажатию play.** Копим
реальные секунды между тиками `timeupdate` (`playMeterTick`), порог —
половина трека или 4 минуты. Считать по `currentTime` нельзя: перемотка вперёд
накручивала бы счётчик, а повтор трека не засчитался бы вовсе. Промежуток
больше 5 секунд между тиками отбрасываем — это перемотка, сон устройства или
заторможенная фоновая вкладка.

## Расширенный скан

`get_metadata` читает ещё год, жанр, номер трека, длительность, битрейт и
album artist. Длительность с битрейтом берутся из `audio.info`, который mutagen
и так разбирает при открытии файла, — лишнего чтения с диска нет (0.45 с на 725
файлов, как и было).

В записи каталога поля лежат под короткими ключами (`yr`, `gen`, `trk`, `dur`,
`br`, `aart`) и **пустые не кладутся**. Это не косметика: каталог целиком лежит
в localStorage, квота 5 МБ, и шесть полных ключей с пустыми строками на трек её
бы дожали. Сейчас две библиотеки занимают 1.30 МБ из 5.

Покрытие сильно зависит от источника: у рипов жанр есть у 95% файлов, у
скачанного из ВК — у 2.5%, год 100% против 19%.

## Периоды прослушивания («эры») и умные плейлисты

Каталог отсортирован от свежих треков к старым, пользователь размечает пачки
номеров годами, из разметки собираются плейлисты «Слушал в 2016».

**Границы хранятся якорями, а не номерами.** Якорь — обезномеренное имя файла
на краю диапазона. Номер как граница жил бы до первого импорта. С якорем всё
сходится само: проверено полной перенумерацией каталога (2440 файлов сдвинуты
на +1, сверху вставлен новый трек) — границы остались **на тех же треках**,
размеры периодов не изменились.

**Период, начинающийся с первого трека, открыт сверху** (`open_start`). Новые
треки приходят наверх каталога и должны попадать в текущий год сами, без правки
границ. В том же тесте новый трек всосался в самый свежий период, 397 → 398.

**Якорь ищется ближайший к сохранённому номеру, а не первый совпавший.** В
каталоге встречаются файлы с одинаковым именем после снятия номера (в этой
библиотеке 69 пар), и первое совпадение растягивало период на 28 треков.
Перенумерация сдвигает файл на единицы позиций, так что ближайший — он и есть.

**Ввод — в номерах файлов, а не в позициях списка.** Они расходятся: в
нумерации бывают пропуски, и здесь разошлись 2435 файлов из 2440.
`eraFileNo` / `eraPosOfNumber` переводят одно в другое, а окно показывает, какие
треки легли на края, — иначе проверить себя невозможно.

**Разрешение якорей делает клиент**, сервер — только хранилище
(`<каталог>/.vinyl_eras.json`) и точка синхронизации между устройствами.
Поэтому разметка и умные плейлисты одинаково работают офлайн: список треков,
счётчики и разметка уже лежат на клиенте.

Умные плейлисты (`buildSmartPlaylists`) состав не хранят, а вычисляют. Экран
разбит на два раздела с постоянными заголовками — «Умные плейлисты» и «Мои
плейлисты»: природа у них разная (состав вычисляется против составленного
руками), и без явной границы список читался как один. Кнопки разложены по
смыслу: «Периоды» настраивает умные, «Создать» — пользовательские; у пустого
раздела своя строка-подсказка вместо тишины.

Карточка общая (`plCardHtml`), отличий два — у умных нет перетаскивания и
редактирования. `findPlaylist` ищет по обоим спискам, поэтому воспроизведение и
кэширование работают одинаково; операции правки намеренно остались на
`userPlaylists.find`. Счётчик в шапке (`plHeaderText`) считает оба списка —
«0 плейлистов» при трёх видимых карточках выглядело ошибкой.

## Радиостанция

Бесконечный поток по критериям, всё считается локально — в сеть станция не
ходит ни разу, поэтому работает и офлайн (пул сам сужается до кэша).

**Критерии выведены из того, чем реально располагает библиотека,** а не из
теории. Замеры перед проектированием: жанр был у 24% треков, год у 38%,
длительность у 100%, lossless 725 файлов. Отсюда живой счётчик подходящих
треков в окне — без него непонятно, почему станция вдруг крутит полтора
альбома. Периоды и активность покрывают всё и потому сильнее жанра.

Оси отбора: периоды прослушивания (только если размечены), жанры, год выпуска,
активность (любые / часто / редко / ещё не слушал / давно не слушал), характер
подбора и флаги lossless / только кэш / без коротких.

**Жанры схлопываются по корню, русский и английский — в одну корзину.** В тегах
одно и то же пишут как «Alternative», «Alt. Rock», «Alternative & Indie»,
«ALTERNATIVE/EXPERIMENTAL», «alternetive» с опечаткой, «альтернатива»,
«Альтернативный рок» — на живой библиотеке выбор дробился на 33 пункта, где
половина синонимы. Корни в `RADIO_GENRE_ROOTS` намеренно **обрезанные**
(`altern`, `альтернат`, `хип`, `электро`): полные слова ловили лишь часть
написаний, префикс ловит все, включая опечатки. **Порядок значим**:
«альтернативный рок» должен попасть в alternative, а не в rock, поэтому узкие
корни идут раньше «поп» и «рок». После схлопывания: alternative 260 вместо трёх
корзин, rock 48, pop 29, hip-hop 22.

Та же нормализация используется и в `buildContinuation`: раньше он сравнивал
жанры сырыми строками, и «Alternative» с «Alt. Rock» веса друг другу не давали.

**«Часто» и «редко» — доля, а не порог по числу прослушиваний.** Порог
вырождается: послушайте все треки поровну, по четыре раза, — и верхний квартиль,
и нижний равны четырём, условие «не меньше четырёх» выполняется для всей
библиотеки, и «часто слушаю» перестаёт что-либо отбирать; с «редко» то же самое
с другой стороны. Поэтому `radioActivityRank` берёт верхнюю и нижнюю четверть
рейтинга прослушанного — это всегда относительно активности самого
пользователя. Проверено: при ста треках, послушанных по четыре раза, в каждую
группу попадает 25, а не 100. Равные счётчики разводятся по давности
прослушивания, иначе на ровном распределении порядок был бы случайным; на
короткой истории четверти не пересекаются.

**Фильтр по году отсекает и треки без года.** Иначе «музыка 2010-х» тихо
притаскивала бы половину библиотеки, у которой года в теге нет.

**Правка критериев на ходу не обрывает музыку.** `applyRadioChanges` оставляет
сыгранное и текущий трек, пересобирая только хвост очереди
(`playQueue.slice(0, playQueuePos + 1)`). Кнопка в плеере (`radioBtn`) видна,
только пока станция ведёт.

**Плавные переходы — только на десктопе, и это осознанно.** На iOS
`audio.volume` не действует (громкость аппаратная), поэтому затухание там можно
сделать лишь через Web Audio — а `createMediaElementSource` дорога в один конец:
после неё звук элемента идёт исключительно через `AudioContext`, и усыплённый в
фоне контекст означает тишину при работающем на вид плеере. Ради украшения
ломать фоновое воспроизведение нельзя, поэтому на iOS опции просто **нет в
списке** — там же, где уже спрятан ползунок громкости, и по той же причине
(`_volumeWorks` = не iOS плюс реальная проверка присваивания).

Рампа считается **по реальному времени, а не по числу шагов**: в неактивной
вкладке `setInterval` зажимается до секунды, и пошаговая рампа растягивалась бы
на минуты, а трек не переключался бы вовсе (поймал это на стенде). По времени
она доходит до конца при любой частоте тиков, просто грубее.

Гасим на исходе трека и сразу зовём `nextTrack`, не дожидаясь `ended`: иначе
последние секунды были бы просто тишиной. Любой выход — ручное переключение,
выключение станции, движение ползунка — обязан вернуть громкость через
`fadeCancel`, иначе оборванная рампа оставила бы музыку тихой до перезапуска.

**Досыпаем заранее**, за пять треков до конца очереди: добор ровно в момент
окончания дал бы паузу между песнями на время отбора.

`buildContinuation(pool, variety)` общая с автопродолжением: станция передаёт
свой отбор, обычная очередь — ничего. `variety` двигает веса случайности и
истории («знакомое» ↔ «сюрприз»).

**Станция выключается при явном выборе музыки** — `playPlaylist`,
`playFromPlaylist`, `playFromList`, `playFromAlbum`, `buildDefaultQueue` (смена
каталога, поиск, сортировка). Пользователь попросил конкретное, значит станция
больше не ведёт, и интерфейс возвращается к обычному.

**Рамка станции лежит ВНУТРИ `.vinyl-side`.** Та объявлена как
`inset: 0; right: 360px`, то есть кончается ровно там, где начинается столбец со
списком, — поэтому рамка физически не может на него заехать и сама едет при
сворачивании панели, без единой строчки на пересчёт координат.

Слоёв два, и это не украшательство: `.radio-glow` — кольцо из вращающегося
конического градиента, у которого маской (`mask-composite: exclude`) вырезана
середина; `.radio-halo` — мягкое свечение внутрь через `inset box-shadow`.
Одним элементом не выходит: `box-shadow` на кольце срезается той же маской.

**Появление и исчезновение — `transition: opacity` на родителях, пульсация —
`animation` на внутреннем слое.** Если повесить и то, и другое на один элемент,
бесконечная анимация перебивает переход, и плавного появления не получается.

Цвет берётся из обложки: `extractColor` уже считает среднее, но затемняет его в
0.45 под фон — рамке нужен неприглушённый, поэтому `setRadioAccent` вызывается
до затемнения. Три оттенка выводятся через HSL, а не сложением к RGB: у тёмной
или блёклой обложки сложение давало бы грязно-серое кольцо вместо переливов,
поэтому насыщенность поднимается принудительно, а светлота держится в коридоре
0.5–0.68.

**Ловушка при проверке:** `getComputedStyle(...).opacity` во время идущего
перехода или анимации отдаёт промежуточное значение — ноль там не означает, что
рамка не работает. Смотреть надо на скриншот и на состояние после того, как
анимации отработали.

## Автопродолжение очереди

Раньше в конце очереди стоял `playQueuePos = 0` — после альбома начиналась
музыка «сначала списка». Теперь `buildContinuation()` досыпает порцию из
**локальной библиотеки**, без единого запроса в сеть, поэтому работает и офлайн
(там кандидаты ограничены кэшем).

Вес: тот же артист, тот же период прослушивания, тот же жанр, близкий год
выпуска, число прослушиваний, плюс случайная добавка — без неё продолжение
всегда одинаковое. Недавно игравшее (последние 150 позиций очереди) исключается.

**Квота на артиста обязательна.** Без `CONT_PER_ARTIST` вес «тот же артист»
перевешивал всё: после трека Oxxxymiron продолжение целиком состояло из
Oxxxymiron (25 из 25). С квотой — 14 артистов на порцию из 25.

## «Играть следующим»

Выбранный трек хранится **по имени файла** (`_forceNextFile`), не по индексу:
`tracks` пересобирается при перезагрузке каталога, поиске и сортировке, и
индекс начинал указывать на другую песню.

Главное для iOS: этот трек добавляется в `nearSet` внутри `prepareNearbyBlobs`
и прогревается вместе с соседями по очереди. Раньше он не входил в «ближние»,
его блоб вытеснялся как далёкий, и переключение с виджета или экрана блокировки
попадало на неподготовленный трек — в фоне загрузка по сети затормаживается, и
музыка молчала до открытия приложения. Команда `next` от виджета идёт через тот
же `nextTrack()`, поэтому чинится и она.

Смена каталога снимает отметку: она относилась к прежнему списку.

## iOS: что можно и чего нельзя

Нельзя автоматически вернуть себе Now Playing после того, как аудио перехватило другое
приложение: iOS отдаёт слот перехватчику и назад не возвращает, события «прерывание закончилось»
в вебе нет, `play()` без жеста заблокирован. После холодного старта PWA не появится в Пункте
управления, пока не проиграет звук по жесту.

Что делается вместо этого: `mediaSession.playbackState` всегда актуален (`'none'` — повод для
iOS выкинуть страницу из Пункта управления), трек и позиция сохраняются вне страницы и
восстанавливаются **на паузе** — первое нажатие продолжает, а не начинает заново.

Автозапуска при восстановлении нет намеренно.

## iOS: пауза с экрана блокировки

Симптом был такой: музыка играет, экран заблокирован, пауза с виджета
срабатывает — а плей уже нет. Держался месяцами и выглядел как «через раз».

**Причина — усыплённый `AudioContext` скретча.** На iOS контекст рождается в
состоянии `suspended`, и `resume()` в обработчике первого `touchstart`
(`unlock`) его не поднимал: в журнале `ac=suspended`, `act=0.0` — ни одного
отрендеренного сэмпла за всё время работы приложения. По-настоящему контекст
включался, только когда пользователь крутил пластинку и `startScratch` звал
`resume()` повторно.

А работающий контекст, как выяснилось, и держит аудиосессию живой. WebKit
считает категорию AVAudioSession по составу слышимых сессий: пока играет
`<audio>` — `Playback`; после `pause()` в фоне слышимых сессий не остаётся,
категория снимается, сессия деактивируется, и поднять её из фона страница уже
не может. Работающий WebAudio-контекст этот провал закрывает.

Отсюда и вся «случайность»: локскрин работал ровно у тех запусков, где
пользователь успевал поскретчить. Это же объясняет, почему откат на три
версии назад (включая июньскую, где нет ни `setAudioSrc`, ни `playbackState`)
ничего не менял — контекст вёл себя одинаково во всех.

Замер, на котором это разделилось:

| Пауза | Контекст в момент паузы | Плей с локскрина |
|---|---|---|
| в приложении | `ac=suspended act=0.0` | не играет |
| в приложении | `ac=running` | играет |
| с локскрина | `ac=running` | играет |

**Починка — `acRevive`.** Будит контекст отовсюду, где на это есть права:
из жеста (слушатель **не снимается** после первого касания — в этом и была
ошибка), из обработчиков `play` и `pause` виджета (MediaSession исполняется с
правами жеста — единственная точка, доступная при заблокированном экране), при
возврате на передний план и по событию `playing` основного элемента. Решающий
вызов — тот, что в **паузе**: контекст поднимается ровно в ту секунду, когда
сессия иначе была бы отпущена.

**Жест — это `touchend` и `click`, но не `touchstart`.** С `touchstart` промис
`resume()` висел «пустышкой» по восемь секунд и разрешался только при смене
видимости, вместе со всеми накопившимися.

**`audioCtx.state` врёт.** В журнале ловилось `ac=running` при `act=0.0`,
державшееся полминуты: контекст рапортует, что работает, и не рендерит ни
одного сэмпла. Верить надо росту `act` (`audioCtx.currentTime`) между
снимками, а не полю `state`.

**Батарея.** Работающий контекст держит поднятым аудиотракт, и на паузе это
заметный нагрев и утечка заряда — пользователь видел это на устройстве. Пока
музыка играет, тракт работает всё равно, и контекст бесплатен. Поэтому
`acIdleArm` усыпляет его через `AC_IDLE_MS` (2 минуты) паузы, а старт
воспроизведения и обработчики виджета будят обратно. Плата: пауза дольше этого
срока возвращает прежнее поведение.

Тупики, каждый закрыт замером, — чтобы не проходить заново:

* офлайн-кэш ни при чём: `blob:` из IndexedDB и поток с сервера дают построчно
  одинаковые журналы;
* громкость ни при чём: `audio.volume` на iOS инертен;
* перемотка не будит: присваивание `currentTime` проходит, часы стоят;
* цикл `pause()` + `play()` не будит;
* `load()` в фоне виснет на `readyState=1` со `stalled` до разблокировки;
* беззвучный второй `<audio loop>` вредит: виджет мигает состоянием, `play()`
  основного элемента виснет без ответа, сыплется `AbortError`;
* пауза через `muted` вместо `pause()` вредит катастрофически — iOS отдаёт слот
  Now Playing другому приложению прямо в момент нажатия;
* подмена `src` в фоне уводила Now Playing чужому приложению.

Остаточное поведение, уже не критичное: `play()`, выданный при неактивной
сессии, оставляет элемент в состоянии «играю, а часы стоят», и оно не проходит
само даже на переднем плане. `resumeWatch` это ловит, а `recoverCycle` /
`recoverReload` чинят — но **при возврате экрана**, не в фоне, где `load()`
всё равно висит.

## Виджет на экране блокировки

**Вид кнопок выбирает система по составу зарегистрированных команд.** Есть
`previoustrack` / `nexttrack` — рисуются стрелки треков, и **полоса прокрутки
пропадает**. Их нет — рисуются кнопки перемотки ±15 секунд вместе с полосой.
Нам нужен второй вид, поэтому навигационные команды **не регистрируются
вовсе**, а переключение треков висит на `seekbackward` / `seekforward` (так
было и исторически). Одна строка на возврат стрелок, если понадобится.

Побочная польза: вид виджета читается прямо из журнала. `ms:seekfwd` — были
кнопки перемотки, `ms:next` — были стрелки. Спрашивать пользователя не нужно.

**Не перерегистрировать обработчики на каждый показ страницы.** Такая правка
была, пользы не дала, а система перечитывает набор команд при каждой
разблокировке — виджет менял вид и пропадал целиком.

**А вот метаданные на возврате публиковать обязательно, даже те же самые.**
Это единственный рычаг вернуть себе Пункт управления после чужого перехвата
(`refreshNowPlaying`). Дедупликация «тот же трек — не публикуем» этот рычаг
ломает; повтор здесь не мусор.

**Состояние кнопки выставлять после метаданных, а не до.** Публикация
метаданных сбрасывает вид кнопки, а обложка приезжает асинхронно — то есть
позже нашего `setMediaPlaybackState`. Отсюда «кнопка плей/пауза врёт, потом
сама выправляется». Точка одна — `syncPlaybackState`, и она же решает, чей
сейчас транспорт: основной элемент или отрывок из DROPS.

**Поздний ответ по обложке затирал новый трек.** `updateMediaSession` держит
поколение (`_msGen`), и колбэк `getCachedCover` проверяет его **до** создания
blob-URL — иначе ссылка утекает, а `revokeObjectURL` отзывает чужую.

## Отрывки DROPS и виджет

Отрывок играет в своём `<audio id="previewEl">`, и транспорт на время
воспроизведения принадлежит ему: обработчики `mediaSession` спрашивают
`previewOwnsTransport()` (так же, как давно делает `togglePlay`), стрелки ходят
по трекам того же релиза через `previewSkip`, виджет получает метаданные
релиза. Без этого кнопка показывала «плей» у звучащего отрывка, а нажатие
запускало совсем другой трек из библиотеки.

**`removeAttribute('src')` не отпускает элемент.** По спецификации снятие
атрибута не запускает алгоритм загрузки, `currentSrc` остаётся прежним — и
`previewOwnsTransport()` продолжал считать транспорт своим после конца
отрывка. Нужен `previewAudio.load()` следом, в обоих местах выгрузки.

**Пауза основного элемента при старте отрывка — не наша пауза.**
`playPreview` зовёт `audio.pause()`, событие уходит в очередь, а
`enterPreviewPlayerUI` синхронно ставит «играет»; отложенный обработчик потом
переписывал состояние на «пауза», пока отрывок звучал. Обработчик `pause`
основного элемента уступает, когда транспорт у отрывка.

`refreshNowPlaying` тоже уступает — иначе при каждой разблокировке виджет
перекрывал релиз библиотечным треком.

## Журнал медиа-событий

Профиль → «Журнал медиа-событий». Пишет в localStorage (`_vc_medialog`, 80
записей) вызовы обработчиков `mediaSession`, события `<audio>`, переходы
`visibilitychange` / `pagehide` / `freeze` / `resume` и тик раз в пять секунд,
пока идёт воспроизведение. Рядом с записью — снимок состояния: `hid`/`vis`,
`paused`, `readyState`, источник (`blob`/`http`), `currentTime`, громкость, и
пауза с предыдущей записи.

Отлаживать локскрин иначе нечем: Web Inspector требует кабеля и Mac под рукой,
а нужное состояние живёт ровно те секунды, пока экран заблокирован. Тик идёт по
`timeupdate`, а не по `setInterval`: таймеры в фоне зажимаются, а события
элемента приходят, пока он действительно играет.

**Отсутствие записи — тоже результат.** Так закрылась версия про заморозку
процесса: `ms:play` в журнале был, значит команда доходила и обработчик
выполнялся.

Регистрация обработчиков идёт через `setMediaAction`, которая пишет отказ
(`ms:reject`). Раньше `try/catch` вокруг `seekbackward` / `seekforward` молчал,
и отказ iOS было не отличить ни от чего.

**Сбор выключается** («Сбор журнала» в профиле): при выключенном журнале не
собирается снимок состояния в обработчиках, не идёт пятисекундный тик по
`timeupdate` и ничего не пишется в localStorage. Записи «Метка» и само
переключение идут в обход — иначе выключенный журнал не зафиксировал бы даже
собственное выключение.

**Кнопка «Метка»** спрашивает, что именно наблюдалось (вид кнопок, врущая
кнопка плей/пауза, кнопки не нажимаются): состояние виджета из кода не
прочитать, а метка без пояснения в разборе бесполезна.

Отдельно пишутся: `app:start` (холодный старт, с пометкой `pwa`/`browser`),
`ms:seekto` (двигали полосу прокрутки — значит виджет был в нужном виде),
`play>rej` с кодом ошибки. Последнее важно: отказ `play()` пользователь видел
тостом, а журнал молчал. `AbortError` там штатный — `selectTrack` запускает
поток и тут же подменяет источник на блоб из кэша; тревожен `NotAllowedError`,
это запуск вне жеста.

**`selectTrack` начинает трек с нуля.** Он обнуляет `_pendingSeek`, поэтому
ветка отказа `play()` откатывала песню в начало — в журналах это видно как
`t=0.0` сразу после `AbortError`. Перезапуск с сохранением места делает
`reloadCurrentKeepingPos`: позиция выставляется **после** `selectTrack`, её
подхватывает `applyPendingSeek`.

## Локальный запуск для проверок

Не трогать запущенный экземпляр пользователя. Изолированный инстанс на своих портах:

```python
import importlib.util, sys, pathlib, time, socketserver
spec = importlib.util.spec_from_file_location("vp", "/путь/vinyl_player.py")
vp = importlib.util.module_from_spec(spec); sys.modules["vp"] = vp; spec.loader.exec_module(vp)
vp.SERVER_PORT = 17656; vp.LOCAL_PORT = 17666
vp.CERT_FILE = pathlib.Path("test_cert.pem"); vp.KEY_FILE = pathlib.Path("test_key.pem")
vp.IS_PUBLIC = True
vp.Handler._get_user = lambda self: next(iter(vp.load_users()))   # обойти авторизацию
# ВНИМАНИЕ: многопоточность удобна, но искажает замеры — настоящий сервер
# однопоточный. Всё, что касается нагрузки (прогрев обложек, стриминг), проверять
# БЕЗ этой обёртки, иначе задержки выйдут приукрашенными.
class T(socketserver.ThreadingMixIn, vp.ReusableHTTPServer): daemon_threads = True
vp.ReusableHTTPServer = T
vp._start_server("0.0.0.0")
while True: time.sleep(1)
```

Важно:
* сервер читает `HTML_PAGE` при импорте — **после правки JS перезапускать процесс**;
* браузер отдаёт страницу из SW-кэша — перед проверкой снимать регистрацию SW и чистить
  `caches`, иначе тестируется старый билд (наступал на это несколько раз);
* `/api/public` и `/api/cert/renew` пишут в общий `~/.vinyl_settings.json` — в тестах не дёргать;
* **подмены `get_user_folders` мало.** Открытый в браузере каталог сервер регистрирует
  пользователю навсегда: путь песочницы уехал в `~/.vinyl_users.json`, и в `folders`, и в
  `last_folder`. Наступал на это. Либо подменять весь `USERS_FILE`, либо после тестов чистить
  запись (права вернуть `chmod 600`);
* теги пишутся **в сам файл**, поэтому проверять запись только на копиях (`shutil.copy2`).
  Жёсткие ссылки для этого не годятся: они делят inode, и правка тега изменила бы оригинал;
* после тестов чистить `indexedDB.deleteDatabase('vinylCache')` и `'vinylNew'` — иначе на диске
  остаются гигабайты закэшированных треков;
* файлы пользователя подменять на песочницу (`RELEASES_FILE`, `STARRED_FILE`, `PLAYS_FILE`,
  `ART_DIR`, `CERT_FILE`, `KEY_FILE`), иначе тесты засорят рабочие данные;
* `.vinyl_eras.json` и `.vinyl_playlists.json` пишутся **внутрь каталога музыки**, поэтому
  каталог тоже подменяем: песочница из жёстких ссылок (`ln`) на настоящие файлы места не
  занимает, а переименования в ней не трогают оригиналы —
  `vp.get_user_folders = lambda u=None: [SANDBOX]`;
* в headless-подобном Chrome медиа не проигрывается (`readyState` не выходит из 0), логику
  воспроизведения проверять подменой `duration` / `currentTime` на элементе.

Проверка синтаксиса перед запуском:

```bash

# и node --check для JS, вытащенного из HTML_PAGE / SW_JS
```

## Конвенции

* Язык в коде смешанный, и это устоявшаяся практика: построчные комментарии почти всегда
  английские (в JS 404 из 408, в Python 212 из 229), а **docstring-и функций — русские**
  (40 из 60). UI-строки и сообщения пользователю — по-русски. Комментарии объясняют
  **почему**, а не что.
* Стиль JS — строго ES5: во всём приложении ноль стрелочных функций и ноль `let`/`const`,
  только `var` и `function`. Сборки и зависимостей нет. Писать так же.
* Файлы состояния — в `$HOME`: `.vinyl_users.json`, `.vinyl_settings.json`, `.vinyl_cert.pem`,
  `.vinyl_key.pem` (все `chmod 600`). Плейлисты — `.vinyl_playlists.json` внутри каталога музыки.
* Правки в большой файл удобнее вносить точечными заменами по уникальной строке с проверкой
  `assert s.count(old) == 1`, а не переписыванием блоков.
